# Отношение с типом и основанием; эталон — частичный порядок, сравнение по транзитивному замыканию

## Context and problem statement

Работа A могла предшествовать B по технологии, из-за одной бригады, задержки поставки или
административного решения. Порядок в графике ТТК или в истории проекта сам по себе не говорит,
какая из причин действует. Эталон должен:

- различать обязательные связи и слабые (предпочтения, неизвестные);
- хранить для каждой связи основание, источник и место в источнике;
- не наказывать эквивалентные наборы дуг (A→B→C и A→B→C плюс A→C — один порядок);
- поддерживать варианты технологии (параметры семейства: стяжка есть или нет и т. п.);
- явно хранить пары, которые выглядят связанными, но технологически независимы.

Пилотные данные: семейства `monolithic_floor` (ТТК 2004, СП 435) и `flat_roof`
(ТТК «Филизол» 2001, СП 71, ТТК 1991), реестр `data/sources.yaml`.

## Considered options

1. Эталон — одно историческое расписание (порядок строк графика ТТК или проекта).
2. Эталон — набор дуг; сравнение дуга-в-дугу.
3. Эталон — операции с пред-/постусловиями и отношения с типом, основанием и источником;
   сравнение по транзитивному замыканию обязательных отношений.

## Decision outcome

Выбран вариант 3.

### Файлы

- `data/sources.yaml` — реестр источников: `id`, `title`, `role`
  (`tech_card` / `normative_sequence` / `expert`), `format`, `volume`, `access`, `license`, `url`.
- `data/families/<family>/<family>.yaml` — словарь операций и описание семейства (поля — в
  разделе «Операции и семейство»).
- `data/families/<family>/<family>_relations.yaml` — `relations`, `interface_relations`, `non_relations`.

### Операции и семейство

Операция (`operations[]`):

| Поле | Обязательно | По умолчанию | Смысл |
|---|---|---|---|
| `id` | да | — | `<ПРЕФИКС>.<ИМЯ>`, уникален в семействе |
| `name` | нет | `""` | название операции |
| `kind` | нет | `""` | `work`, `control` или `safety` |
| `requires` | нет | `[]` | состояния, которые операция потребляет |
| `requires_if` | нет | `{}` | `параметр: [состояния]`; действуют только при истинном параметре |
| `produces` | нет | `[]` | состояния, которые операция производит; у состояния ровно один производитель |
| `zone` | нет | — | зона работ; справочное |
| `ttk` | нет | — | пункты источников, из которых взята операция; справочное |
| `schedule_row` | нет | — | номер строки графика ТТК (разд. 5); `null` — операции нет в графике; у семейства без графика (`flat_roof`) поле не задаётся; справочное |
| `note` | нет | — | пояснение; справочное |

Верификатор читает `id`, `name`, `kind`, `requires`, `requires_if`, `produces`; остальные
поля нужны человеку и в проверках не участвуют.

Семейство (верхний уровень файла):

| Поле | Обязательно | Смысл |
|---|---|---|
| `operations` | да | список операций |
| `parameters`, `optional_operations` | нет | параметры семейства и операции, которые входят в экземпляр только при истинном параметре; без параметров семейство даёт один экземпляр |
| `external_inputs`, `external_outputs` | нет | внешние входы и выходы семейства |
| `family`, `name`, `scope` | нет | описание семейства; справочное |
| `resources_note` | нет | ресурсы, которые есть в графике ТТК, но не являются операциями (например, работа крана); справочное |

### Отношение (`relations`)

| Поле | Значения | Правило |
|---|---|---|
| `id` | `F<n>-R<k>` | стабильный: не перенумеровывается, номер удалённого отношения не переиспользуется; при пересмотре концов, типа или основания связь сохраняет `id` |
| `from`, `to` | id операций семейства | |
| `type` | `mandatory`, `conditional`, `preferred`, `unknown` | |
| `condition` | имя одного параметра семейства | обязательно для `conditional`, запрещено для остальных |
| `basis` | подмножество `object_state`, `result_consumption`, `zone_access`, `tech_card`, `statistical_repeat` | непусто для `mandatory` и `conditional` |
| `sources` | список `{source, locator, note}` | `source` — id из `sources.yaml`; у `SRC.EXPERT` `locator: null` |
| `status` | `source_checked`, `needs_check`, `expert_needed` | у `SRC.EXPERT` — `expert_needed`, пока эксперт не подтвердил |
| `lag` | текст | справочное; в FS-модели не используется |

Строка графика производства работ ТТК допускается как источник порядка; причина, по которой
порядок обязателен, указывается в `basis` и `note`. Совпадение строк или отметок графика причиной
не является. Если ТТК задаёт порядок только строкой графика, а причину называет автор, ребро
получает `status: expert_needed` и второй источник `SRC.EXPERT` с причиной в `note`
(примеры — F1-R30 и F1-R31; для F2-R11 источник в ТТК не найден, остался только `SRC.EXPERT`).
Если найденная причина относится к другой операции, чем строка графика, ребро ведёт к той
операции, которую причина действительно касается (F1-R31 ведёт к палубе перекрытия, а не к
рамам и стойкам из следующей строки графика), а пара из графика записывается в `non_relations`.

### Согласованность операций и отношений

- Каждое состояние из `requires` (и активного `requires_if`) производит ровно одна операция
  или внешний вход.
- Пара «производитель → потребитель» состояния есть в отношениях с типом `mandatory` или
  `conditional`, и наоборот: каждое такое отношение опирается на `requires`.
  `preferred` и `unknown` в `requires` не отражаются.

### Экземпляры семейства

Экземпляр задаётся значениями параметров. Операция из `optional_operations` входит в экземпляр,
только если её параметр истинен. Отношение входит в экземпляр, если выполнено его `condition`
и обе его операции есть в экземпляре. Все проверки выполняются для каждого экземпляра отдельно.

### Эталон и сравнение

- Эталон экземпляра — транзитивное замыкание отношений `mandatory` и активных `conditional`
  между операциями экземпляра.
- `preferred` и `unknown` в замыкание не входят и учитываются отдельно; `unknown` в ответе
  модели не считается ложным автоматически.
- TP / FP / FN считаются по парам замыкания; избыточные дуги эталона и ответа на метрику не влияют.
- Основная оценка считается по подтверждённой части эталона, пары неподтверждённых рёбер
  маскируются; оценка по полному эталону — дополнительная (раздел «Неподтверждённые рёбра и их
  учёт в метрике»).
- Внешние связи (`interface_relations`) в метрику не входят и проверяются как покрытие.

### Внешние связи (`interface_relations`)

Поля `id`, `from`, `to`, `cause` (`interface` / `supply`), `basis`, `sources`, `status`.
`basis: []` допустим только при `cause: supply`: причина такой связи — поставка, она указана в `cause`.

### Подтверждённые независимости (`non_relations`)

Пара операций с причиной (`reason`), почему порядок между ними — не технология (одна бригада,
поставка, параллельные работы). Ни в одном экземпляре пара не должна быть связана путём
в замыкании эталона. Используются для проверки эталона, негативных тестов
(«лишняя историческая связь») и разбора FP baselines.

### Принятые упрощения

- Только связи типа FS; совмещение «на себя» (ТТК «Филизол», п. 2.8) упрощено до FS.
- Альтернативные способы (подача бетона краном или насосом) свёрнуты в одну операцию.
- Очистка арматуры даёт одно состояние `reinforcement.cleaned` для стен и перекрытия.
- `WALL.REINFORCEMENT_CLEAN` и `WALL.OPENINGS_CLOSE` — самостоятельные этапы без предусловий.
- Состояния `wall_concrete.cured`, `slab_concrete.cured`, `slab_supports.removed` производятся,
  но ни одна операция их не требует: это итоговые состояния этапов (уход за бетоном, демонтаж
  стоек), после которых в семействе нет работ. Верификатор такие состояния не считает ошибкой.

### Consequences

- Верификатор проверяет: цикл; непокрытую операцию; отношение без основания; согласованность
  `requires` и отношений; `non_relations`; сравнение замыканий — по каждому экземпляру.
- Одно ошибочное обязательное ребро порождает несколько ложных пар замыкания (все предки × все
  потомки), поэтому слабые связи нельзя включать в эталон «на всякий случай».
- Рёбра со статусом `needs_check` и `expert_needed` входят в полный эталон, а в основной оценке
  их пары маскируются (см. «Неподтверждённые рёбра и их учёт в метрике»).
- Рёбра, порядок которых взят из графика ТТК, — риск принять диспетчерский порядок за технологию;
  их список и причины видны по `locator` и `note`.

### Неподтверждённые рёбра и их учёт в метрике

Сейчас не подтверждены источником:

| Семейство | Ребро | Тип | Статус |
|---|---|---|---|
| `monolithic_floor` | F1-R09, F1-R10, F1-R19, F1-R30, F1-R31 | `mandatory` | `expert_needed` |
| `monolithic_floor` | F1-R16 | `mandatory` | `needs_check` |
| `monolithic_floor` | F1-R14 | `preferred` | `expert_needed` (в замыкание не входит) |
| `flat_roof` | F2-R11 | `mandatory` | `expert_needed` |

Полный эталон `monolithic_floor` — 605 пар замыкания, подтверждённая часть — 367, в маску попадает
238 пар (39 %). Больше всего даёт F1-R19: без одного этого ребра теряется 146 пар. У `flat_roof`
маска — 52 из 1422 пар (4 %) по восьми экземплярам, все от F2-R11.

**Правило оценки.** Для экземпляра:

- `R_full` — замыкание всех `mandatory` и активных `conditional` рёбер (полный эталон);
- `R_conf` — замыкание только тех из них, у которых `status: source_checked` (подтверждённая часть);
- маска `M` — пары из `R_full`, которых нет в `R_conf`, и обратные к ним пары;
- `P` — замыкание `mandatory` рёбер ответа.

Основная оценка: TP = |P ∩ R_conf|, FN = |R_conf \ P|, FP = |P \ (R_conf ∪ M)|. Пары из
`P ∩ M` не дают ни TP, ни FP и отчитываются отдельно; пары из `M`, которых нет в ответе, не дают
FN. Отсутствие подтверждения не превращается в отрицательный эталон: пара из маски не считается
ни обязательной, ни запрещённой.

- Пара, которая выводится и через неподтверждённое ребро, и через путь только из подтверждённых
  рёбер, входит в `R_conf` и оценивается как обычно.
- `unknown` в ответе в `P` не входит и FP не даёт. Пара из `R_conf`, которую ответ пометил
  `unknown`, — FN с отметкой `fn_declared_unknown`.
- Дополнительная оценка — по `R_full` без маски (анализ чувствительности); публикуется рядом
  с основной.
- Подтверждение ребра экспертом переводит его в `source_checked`, и его пары выходят из маски.
  Если при проверке ребро переводится в `preferred` или `unknown`, его пары уходят и из `R_full`.

**Примеры** (`monolithic_floor`, кроме второго):

1. Пара только с неподтверждённым путём. `WALL.PLATFORM_REMOVE → SLAB.FORM_DECK` выводится
   только через F1-R31, поэтому она в `M`. Ответ с этой парой, без неё или с обратной парой
   получает за неё 0 TP, 0 FP, 0 FN.
2. Пара с альтернативным подтверждённым путём. Рёбра A→B (`expert_needed`), A→C и C→B (`source_checked`): (A, B) ∈ `R_conf`.
   Ответ с A→B или с A→C→B — TP; ответ без пути из A в B — FN.
3. `unknown` в ответе. Ответ помечает `unknown` пару `WALL.PLATFORM_REMOVE → SLAB.FORM_DECK`
   (из `M`) — за неё ничего. Ответ помечает `unknown` подтверждённую пару
   `SLAB.REBAR_ACCEPT → SLAB.CONCRETE` и не утверждает её — FN, `fn_declared_unknown`.
4. Пара вне эталона. Ответ утверждает `WALL.PLATFORM_REMOVE → SLAB.FORM_SUPPORTS`: её нет
   в `R_full` и в `M`, это FP, а поскольку пара записана в `non_relations` — ещё и
   `fp_on_non_relation`.

## Pros and cons of the options

- **Историческое расписание.** Просто получить, но переносит ресурсный и случайный порядок
  (например, настил раньше каркасов, приём бетона после закладных) в эталон и не даёт
  основания для связи.
- **Сравнение дуга-в-дугу.** Наказывает эквивалентные наборы дуг: транзитивно избыточное ребро
  засчитывается как ошибка, хотя порядок тот же.
- **Частичный порядок с основаниями.** Требует ручной разметки оснований и источников и
  проверки по экземплярам, но соответствует постановке и позволяет отделить технологию от очереди.
