# Отношение с типом и основанием; эталон — частичный порядок, сравнение по транзитивному замыканию

## Context and problem statement

Задача 1, п. 4: зафиксировать формат отношения между операциями и формат эталона, с которым
верификатор и baselines сравнивают восстановленный граф.

Работа A могла предшествовать B по технологии, из-за одной бригады, задержки поставки или
административного решения. Порядок в графике ТТК или в истории проекта сам по себе не говорит,
какая из причин действует. Эталон должен:

- различать обязательные связи и слабые (предпочтения, неизвестные);
- хранить для каждой связи основание, источник и место в источнике;
- не наказывать эквивалентные наборы дуг (A→B→C и A→B→C плюс A→C — один порядок);
- поддерживать варианты технологии (параметры семейства: стяжка есть или нет и т. п.);
- явно хранить пары, которые выглядят связанными, но технологически независимы.

Пилотные данные: семейства `monolithic_floor` (ТТК 2004, СП 435) и `flat_roof`
(ТТК «Филизол» 2001, СП 71, ТТК 1991), реестр `data/sources.yaml`.

## Considered options

1. Эталон — одно историческое расписание (порядок строк графика ТТК или проекта).
2. Эталон — набор дуг; сравнение дуга-в-дугу.
3. Эталон — операции с пред-/постусловиями и отношения с типом, основанием и источником;
   сравнение по транзитивному замыканию обязательных отношений.

## Decision outcome

Выбран вариант 3.

### Файлы

- `data/sources.yaml` — реестр источников: `id`, `title`, `role`
  (`tech_card` / `normative_sequence` / `expert`), `format`, `volume`, `access`, `license`, `url`.
- `data/families/<family>/<family>.yaml` — словарь операций семейства:
  `id`, `name`, `kind`, `requires`, `requires_if`, `produces`, `zone`, `ttk`, `note`;
  на уровне семейства — `parameters`, `optional_operations`, `external_inputs`, `external_outputs`.
- `data/families/<family>/<family>_relations.yaml` — `relations`, `interface_relations`, `non_relations`.

### Отношение (`relations`)

| Поле | Значения | Правило |
|---|---|---|
| `id` | `F<n>-R<k>` | стабильный: не перенумеровывается, номер удалённого отношения не переиспользуется |
| `from`, `to` | id операций семейства | |
| `type` | `mandatory`, `conditional`, `preferred`, `unknown` | |
| `condition` | имя одного параметра семейства | обязательно для `conditional`, запрещено для остальных |
| `basis` | подмножество `object_state`, `result_consumption`, `zone_access`, `tech_card`, `statistical_repeat` | непусто для `mandatory` и `conditional` |
| `sources` | список `{source, locator, note}` | `source` — id из `sources.yaml`; у `SRC.EXPERT` `locator: null` |
| `status` | `source_checked`, `needs_check`, `expert_needed` | у `SRC.EXPERT` — `expert_needed`, пока эксперт не подтвердил |
| `lag` | текст | справочное; в FS-модели не используется |

Строка графика производства работ ТТК допускается как источник порядка; причина, по которой
порядок обязателен, указывается в `basis` и `note`.

### Согласованность операций и отношений

- Каждое состояние из `requires` (и активного `requires_if`) производит ровно одна операция
  или внешний вход.
- Пара «производитель → потребитель» состояния есть в отношениях с типом `mandatory` или
  `conditional`, и наоборот: каждое такое отношение опирается на `requires`.
  `preferred` и `unknown` в `requires` не отражаются.

### Экземпляры семейства

Экземпляр задаётся значениями параметров. Операция из `optional_operations` входит в экземпляр,
только если её параметр истинен. Отношение входит в экземпляр, если выполнено его `condition`
и обе его операции есть в экземпляре. Все проверки выполняются для каждого экземпляра отдельно.

### Эталон и сравнение

- Эталон экземпляра — транзитивное замыкание отношений `mandatory` и активных `conditional`
  между операциями экземпляра.
- `preferred` и `unknown` в замыкание не входят и учитываются отдельно; `unknown` в ответе
  модели не считается ложным автоматически.
- TP / FP / FN считаются по парам замыкания; избыточные дуги эталона и ответа на метрику не влияют.
- Внешние связи (`interface_relations`) в метрику не входят и проверяются как покрытие.

### Внешние связи (`interface_relations`)

Поля `id`, `from`, `to`, `cause` (`interface` / `supply`), `basis`, `sources`, `status`.
`basis: []` допустим только при `cause: supply`: причина такой связи — поставка, она указана в `cause`.

### Подтверждённые независимости (`non_relations`)

Пара операций с причиной (`reason`), почему порядок между ними — не технология (одна бригада,
поставка, параллельные работы). Ни в одном экземпляре пара не должна быть связана путём
в замыкании эталона. Используются для проверки эталона, негативных тестов
(«лишняя историческая связь») и разбора FP baselines.

### Принятые упрощения

- Только связи типа FS; совмещение «на себя» (ТТК «Филизол», п. 2.8) упрощено до FS.
- Альтернативные способы (подача бетона краном или насосом) свёрнуты в одну операцию.
- Очистка арматуры даёт одно состояние `reinforcement.cleaned` для стен и перекрытия.
- `WALL.REINFORCEMENT_CLEAN` и `WALL.OPENINGS_CLOSE` — самостоятельные этапы без предусловий.

### Consequences

- Верификатор проверяет: цикл; непокрытую операцию; отношение без основания; согласованность
  `requires` и отношений; `non_relations`; сравнение замыканий — по каждому экземпляру.
- Одно ошибочное обязательное ребро порождает несколько ложных пар замыкания (все предки × все
  потомки), поэтому слабые связи нельзя включать в эталон «на всякий случай».
- Рёбра со статусом `needs_check` и `expert_needed` входят в эталон; как их учитывать в метрике,
  решается с руководителем.
- Рёбра, порядок которых взят из графика ТТК, — риск принять диспетчерский порядок за технологию;
  их список и причины видны по `locator` и `note`.

## Pros and cons of the options

- **Историческое расписание.** Просто получить, но переносит ресурсный и случайный порядок
  (например, настил раньше каркасов, приём бетона после закладных) в эталон и не даёт
  основания для связи.
- **Сравнение дуга-в-дугу.** Наказывает эквивалентные наборы дуг: транзитивно избыточное ребро
  засчитывается как ошибка, хотя порядок тот же.
- **Частичный порядок с основаниями.** Требует ручной разметки оснований и источников и
  проверки по экземплярам, но соответствует постановке и позволяет отделить технологию от очереди.
